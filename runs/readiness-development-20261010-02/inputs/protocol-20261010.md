# Human-clarified readiness report comparison

Protocol fixed before the comparison run on 2026-10-10. This is a public development
case, derived from an actual maintainer critique and an elicited human clarification.
The selected option text is preserved verbatim in clarification-20261010.json. It is
not an independently collected external request or a held-out natural-language test.

## Question and contract

Does supplying repository facts and the human-confirmed meaning let simple deterministic
controls produce a valid readiness report while retaining the prior numbers and source?
Does selective reuse avoid unnecessary numeric report regeneration? This case does not
test an AI policy or establish why API credits are necessary.

The final visible document must include current MIT, the successful CI's exact observed
revision and evidence URL, the exact prerelease tag/revision/URL, and explicitly
unestablished external reproduction and AI advantage. It must embed the prior numeric
report unchanged, with source SHA256 and all original policy counts. Snapshot facts
are time-bounded observations, not promises about later repository state.

## Equal information and controls

All controls receive the same original request, entire clarification choices and actual
answer, frozen current facts/evidence, metrics bytes and previous published numeric report.
Both interpretation controls require a confirmed answer and match it to a disclosed choice.
The rule control reads the explicit choice; the clarification control checks completeness
before resolving that same recorded answer. They are deliberately strong, potentially
equivalent controls on this clarified case. Their convergence is a valid negative result.
No answer means unresolved, and no meaning-dependent policy comparison may run.

Five arms: confirmed-requirement B0, rule+B1, rule+B2, clarification+B1, clarification+B2.
B0 is a recomputation reference with confirmed meaning, not an interpretation competitor.
No policy sees evaluator outputs or consumes another arm's generated history. Each starts
from a clone of one measured new seed whose numeric output must equal the actual prior
observed-02/retitled-report.md bytes. This seed is a replay fixture, not an imported old
production cache. The three numeric operations use unchanged code, input and contracts.

## Counts and times

The graph is select -> summary -> render -> compose-readiness. Readiness facts only affect
composition, so the numeric requirements remain unchanged. The current cache has no final
readiness document. Enumerate numeric plans independently and add one mandatory composition
execution: a finite stage-count bound, not a CPU/time/dollar optimum. Count composition
as new work. Record any additional role computations made inside B2 checks separately.

Use five repetitions of this SAME case. Rotate the five-arm order cyclically, putting
each arm at each position once. This diagnoses timing variability; it does not supply
five independent user cases or statistical evidence of generalization. No sleeps, synthetic
weights or performance pass thresholds. Costs: interpretation, planning/integrity/contract
checks, composition, stage regeneration, fallback, complete runtime wall and evaluator
overhead. Nested operation times overlap and must not be summed into wall time. Shared
input preparation/seed and per-arm clone costs are reported separately.

One real human question/answer was obtained; subsequent policy runs replay its record.
Human wait, human repair time, implementation session tokens/cost and local dollar costs
remain unmeasured. Runtime evaluated model calls/tokens/paid API charges are zero. Actual
read-only GitHub fact capture calls and their wall times are recorded separately; they
are not AI model calls or runtime policy calls. These exclusions prevent total human or
monetary savings claims.

## Evaluation and stop rule

After all arms execute, independently reconstruct numeric expectations from original
metrics bytes, parse the visible facts and source fields, and audit every numeric binding,
consumption and publication. Audit readiness consumption/publication hashes and lineage,
including whether cached bytes were actually consumed. Separate interpretation errors,
missing capabilities, invalid reuse and final output failures. Intentionally changed numeric
values, stale facts, missing limitations and invalid provenance must be rejected in tests.

Pass: all five arms satisfy the confirmed document contract and consume no invalid reuse.
If B1/B2 reach the finite execution-count minimum, record simple controls as sufficient
for this case and stop without adding AI. Any failed arm is retained and reported.
